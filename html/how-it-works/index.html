How it works

A review system made of files you can read.

No account, daemon, dashboard, or mystery database. Your agent inspects a one-time installer, installs the two core skills, adds only the approved specialist skills that apply to the project, surveys the repository, and creates an agent-generated, human-owned project doctrine file called .grump.

01

Install

The agent inspects the one-shot installer as untrusted. The two core skills are installed. Specialist skills are proposed only when project evidence shows they apply, and each one requires approval before it is downloaded. The installer itself is not retained.

02

Survey

The agent inspects repository evidence and project documents first. It uses the installed specialist skills to remove resolved and duplicate questions, asks Q001 about doctrine format, asks whether to add GrumpyDev's generated files to .gitignore, and numbers every question it presents.

03

Write doctrine

The agent creates or updates .grump from evidence and explicit answers. Humans own it. Compact and detailed formats preserve the same project-specific decisions, stable identifiers, and relevant execution profiles without storing generic rules or transcripts.

04

Grump

The review uses the project doctrine, the selected plan, architecture, project, diff, or other engineering artifact, relevant project documents, and every installed specialist skill that has not been marked inapplicable. Each specialist checks direct and indirect effects, while supporting detail loads only for materially affected boundaries. The review asks only material allowed questions, downloads no additional skills, and always returns results in chat. Plan addenda and execution rules apply only to implementation plans.

The review contract

Specific criticism or it doesn't count.

Every material finding must connect an observed fact to a plausible failure and a practical response.

EVIDENCEWhat the repository, project documents, reviewed work, or user actually says.
RISKWhat can fail, for whom, and under which condition.
IMPACTWhy the failure matters enough to require a change.
ACTIONThe smallest concrete correction or decision needed.
GRUMP REVIEWREVISE

[HIGH] Retry strategy creates duplicate jobs

The plan retries POST requests after timeouts, but the API client has no idempotency key and the persistence layer records remote job IDs only after the response returns.

Evidence

src/jobs/create.ts and the proposed "retry three times" step.

Required change

Define an idempotency boundary and persist the operation key before the first remote call.

Review depth
MODELUse a reasoning-capable model at medium effort or above. High, xhigh (sometimes labeled extra high), or max is preferred when supported. The review assumes the active agent can reason and does not spend time identifying its own model or effort.
Lean - catch the obvious breakage quickly

Check the highest-risk assumptions and boundaries. Escalate when a fatal assumption, serious risk, or missing fact makes a lean review insufficient.

Standard - the default engineering review

Apply the full default review to the selected target, project evidence, and every relevant technology and engineering boundary.

Deep - assume the incident review is tomorrow

Gather broader evidence and investigate affected boundaries more aggressively without wasting time on unrelated parts of the project.

Verdicts
APPROVE

Sound for its stated purpose.

APPROVE WITH CONCERNS

Proceed with named risks.

REVISE

Fix material gaps first.

REJECT

The approach is fundamentally unsafe or misaligned.

INSUFFICIENT EVIDENCE

The honest verdict when available evidence cannot support a conclusion.
