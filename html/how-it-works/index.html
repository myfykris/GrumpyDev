How it works

A review system made of files you can read.

No account, daemon, dashboard, or mystery database. GrumpyDev works by having your agent install project-local skills, survey the repo, and create the .grump Markdown configuration file. This file is then used to provide the context and specialist judgment to challenge engineering plans before implementation.

01

Install

Your agent reads /install.txt, fetches the manifest, and installs the core and survey skills locally.

02

Survey

It inspects the repository and project documents before asking anything. When execution details can change engineering decisions, it confirms concise runtime and deployment profiles plus any material specialist gaps in one numbered batch. It skips hosting questions when they do not apply.

03

Agree

It writes a proposed .grump with sourced project doctrine and, when relevant, the environments that build, run, or consume the software. You correct or accept it, choose how confirmed decisions are recorded, and approve relevant specialist skills.

04

Grump

Ask it to "Grump this plan." It reads the policies and earlier review history, attacks assumptions, returns a verdict, and appends the result to the plan only when you allowed it.

The review contract

Specific criticism or it doesn't count.

Every material finding must connect an observed fact to a plausible failure and a practical response.

EVIDENCEWhat the repository, project documents, plan, or user actually says.
RISKWhat can fail, for whom, and under which condition.
IMPACTWhy the failure matters enough to change the plan.
ACTIONThe smallest concrete correction or decision needed.
GRUMP REVIEWREVISE

[HIGH] Retry strategy creates duplicate jobs

The plan retries POST requests after timeouts, but the API client has no idempotency key and the persistence layer records remote job IDs only after the response returns.

Evidence

src/jobs/create.ts and the proposed "retry three times" step.

Required change

Define an idempotency boundary and persist the operation key before the first remote call.

Review depth
MODELUse a reasoning-capable model at medium effort or above. High, xhigh (sometimes labeled extra high), or max is preferred when supported.
Quick - catch the obvious breakage

Focus on fatal assumptions, missing dependencies, unsafe sequencing, and contradictions.

Standard - the default engineering review

Trace the plan across architecture, data, operations, tests, rollout, and repository conventions.

Deep - assume the incident review is tomorrow

Investigate edge cases, failure recovery, observability, security, migrations, and reversibility in detail.

Verdicts
APPROVE

Sound enough to implement.

APPROVE WITH CONCERNS

Proceed with named risks.

REVISE

Fix material gaps first.

REJECT

The approach is fundamentally unsafe.

INSUFFICIENT EVIDENCE

The honest verdict when the repository or plan cannot support a conclusion.
