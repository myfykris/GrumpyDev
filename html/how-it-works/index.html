How it works

A review system made of files you can read.

GrumpyDev is plain-text review guidance for your existing coding agent. Set it up in your project, answer questions about what matters, and ask for a review when you want one. No GrumpyDev account or background service is needed.

01

Install

Paste the setup prompt into your coding agent. The installer requires it to inspect the downloaded instructions and get your approval before adding specialist skills.

02

Answer project questions

Answer numbered questions about missing project context and your review preferences. The agent is instructed to read your project first and skip factual questions it can already answer.

03

Save project context

The survey asks your agent to save this context in .grump. Choose compact notes or more explanation, and edit the file yourself whenever you need to.

04

Ask for a review

Show your agent the plan or name its file, then ask: Grump this plan.

For code changes, you can also ask: Grump this diff.

The review instructions require an explicit request and a result in chat.

Later, tell your coding agent: Update GrumpyDev for this project. or Remove GrumpyDev from this project. The maintenance instructions require your agent to ask before replacing files that differ. Unrelated files and instructions must be preserved. Read about updates and removal.

What to expect from a review

Specific criticism or it doesn't count.

GrumpyDev requires the agent to back each objection with evidence, explain what could go wrong, and say what would fix it.

The instructions require the agent to finish the requested review before giving its verdict. Fixing the work does not start another review; ask for one when you are ready.

When earlier reviews are available, the agent is told to recheck previous findings and explain why any new issue appeared.

EVIDENCEWhat the repository, project documents, reviewed work, or user actually says.
RISKWhat can fail, for whom, and under which condition.
IMPACTWhy the failure matters enough to require a change.
ACTIONThe smallest concrete correction or decision needed.
GRUMP REVIEW🛠️ REVISE

Summary

1 HIGH finding. Invoice retries can create duplicate remote jobs.

🔴 GD-001 [HIGH] Retry can create duplicate jobs

Evidence

src/jobs/create.ts::submitJob() and plan section "Job submission".

Established fact

The plan retries after a timeout, the client sends no operation key, and the remote ID is stored only after a response returns.

Conditional risk

A successful first request with a lost response makes the retry unsafe.

Impact

One local operation can produce two remote jobs.

Required change

Define an idempotency boundary and persist the operation key before the first remote call.

Review scope: implementation plan / full / deployment
Review depth

Ask for a quick GrumpyDev review to choose Quick. Otherwise, GrumpyDev's instructions use Full.

MODELUse a reasoning-capable model at medium effort or above. High, xhigh (sometimes labeled extra high), or max is preferred when supported.
Quick - a lighter review

A lighter review of the whole target, focused on the main risks. The agent is instructed to say when a full review is needed to reach a responsible conclusion.

Full - a more thorough review, used by default

A closer investigation of the work, its assumptions and failure cases, and how it could affect other parts of the project.

Verdicts
APPROVE

Sound for its stated purpose.

APPROVE WITH CONCERNS

Proceed with named nonblocking concerns.

REVISE

Fix material gaps first.

REJECT

The approach is fundamentally unsafe or misaligned.

INSUFFICIENT EVIDENCE

The honest verdict when available evidence cannot support a conclusion.
