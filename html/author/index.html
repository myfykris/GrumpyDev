For skill authors

Turn hard-won judgment into a skill.

A good specialist skill teaches an agent what to inspect, which failures hide behind plausible plans, and what evidence earns confidence.

01

Be specific

Name concrete artifacts, invariants, lifecycle transitions, and failure conditions.

02

Be falsifiable

Tell the reviewer what evidence changes the conclusion. Avoid universal rules without context.

03

Be concise

Context is finite. Include knowledge the agent cannot cheaply reconstruct.

What to include

One complete skill. Concise main instructions. Focused detail.

SKILL.md, SURVEY.md, and every supporting reference all belong to the same specialist skill and are installed together.

  • SKILL.md: The initial checks and when to read each supporting file.
  • SURVEY.md: Project questions that affect reviews and where their answers belong in .grump.
  • References: Specific failure cases, what to inspect, and how to tell whether a concern has been addressed.
  • Manifest: The skill's catalog entry, complete file list, and conditions for recommending it during setup.

Shared review and survey procedure belongs in the core skills.

gd-postgresql/
SKILL.md
  Initial checks and when to read more
SURVEY.md
  Project questions and .grump answers
references/review.md
  Detailed failures, evidence, and fixes
references/queries-and-indexes.md
  Checks for affected queries and indexes

Published catalog paths stay readable, while installed specialist names use the gd- prefix to avoid collisions with ordinary project skills. These files are one skill, not separate installations. The core skill instructs the agent to include every applicable installed specialist entrypoint in every explicit GrumpyDev review. Precise routing tells the agent when to load supporting detail.

Reference boundaries

Split only when the split saves context.

Splitting every topic into its own file is a dumb structure. Vague routing and file-per-topic navigation can cost more context than they save.

For PostgreSQL, query and index guidance can live in one reference, with replication and recovery guidance in another. Give each file a clear condition for reading it. Keep topics together when the same review usually needs both.

  • references/queries-and-indexes.md
  • references/operations-replication-and-recovery.md

A query change can still affect replication or recovery, so its review may need both files. If you cannot explain when the extra file is needed, keep the guidance in references/review.md.

Split it when

  • There is enough detailed guidance to justify a separate read.
  • Legitimate reviews can often skip it completely.
  • The entrypoint can state a precise trigger.
  • It adds detailed failure modes, evidence, or verification.
  • It remains independent without routing to another reference.

Keep it in review.md when

  • It applies to almost every full review of that domain.
  • The split would save little context.
  • The trigger would be vague.
  • It repeats the entrypoint or another reference.
  • It would create file-per-topic navigation overhead.
Acceptance checklist
[x]Valid name and manifest inclusion and exclusion conditions that decide applicability before download
[x]Description and body activate only for an explicitly requested GrumpyDev review
[x]Core instructions require every applicable installed specialist in every explicit review unless .grump explicitly marks it inapplicable
[x]Specialists inspect direct and indirect effects without inventing findings
[x]Specialists include SKILL.md, SURVEY.md, and every routed reference
[x]Every skill file is listed in the manifest
[x]SKILL.md remains useful by itself for quick review
[x]review.md adds detailed checks for parts of the project that could be affected, without repeating SKILL.md
[x]Every focused reference has a precise SKILL.md trigger
[x]References never route to more references
[x]SURVEY.md never loads during ordinary review
[x]Quick and full reviews skip unrelated supporting references
[x]No review-time skill or instruction downloads, hidden dependencies, or executable payloads
[x]Include every listed skill file and pass local validation before opening a pull request
How to contribute
  1. Draft the complete skill and its manifest entry
  2. Generate and validate the catalog in a local repository checkout
  3. Open a pull request explaining the mistakes the skill helps review, with concrete examples in the PR description

Maintainers review the contribution before adding accepted skills to the catalog.
