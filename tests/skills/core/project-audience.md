# Project audience review behavior

Expected behavior:

- Define the project audience as the intended recipients of the reviewed
  project's output, not automatically the developer requesting the review.
- Establish audience goals, available context, knowledge, vocabulary, and
  point of encounter from evidence instead of inventing a generic persona.
- Evaluate copy from the recipient's perspective and flag hidden context,
  unexplained terminology, vague claims, generic filler, unsupported promises,
  and hand-wavy language that communicates no concrete meaning or action.
- Do not use a mechanical banned-word list or reject audience-appropriate
  technical language merely because it is technical.
- Evaluate pages, screens, sections, navigation, workflows, messages, and
  documentation before treating sentence-level quality as sufficient.
- Treat an accurate, well-written but unnecessary page as a structural defect.
- Treat a missing audience task, state, page, or path as a defect even when all
  existing copy is good.
- Organize information around audience tasks and decision order rather than an
  internal org chart, implementation boundary, template, or generated layout.
- Evaluate next actions, consequences, errors, recovery, accessibility,
  localization, devices, permissions, and distinct audiences when applicable.
- Do not demand formal research for every change. Ask a deduplicated `RQ###`
  question or report an evidence gap only when the unknown can materially
  change the verdict or required correction.
- Connect findings as `evidence -> recipient mismatch -> failed task or
  consequence -> required change` and identify the affected audience.
- Do not substitute GrumpyDev's tone or the reviewer's stylistic taste for
  evidence about what serves the project audience.
- Execution rules preserve approved project-audience decisions and prevent the
  implementing agent from inventing material audience assumptions, unnecessary
  artifacts, or vague placeholder copy.
