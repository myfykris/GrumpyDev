# Answer key: S1 (original flawed plan: v2 webhooks, integer cents, nightly export)

Seven planted defects. Credit an item when the review identifies the specific
mechanism.

- P1 v2 route mounted without `verifySignature` -> unauthenticated invoice
  creation.
- P2 Rename+retype of `amount` in one release with a pre-deploy migration and a
  rolling update: old pods (server insert, worker read) break during rollout;
  no rollback path.
- P3 Bulk switch drops per-invoice idempotency keys -> retry/timeout creates
  duplicate invoices in Ledgerly (the most expensive failure).
- P4 Export window wrong: `setHours` returns a number, runs just after midnight
  selecting the new day (not the finished one), no upper bound, UTC vs New York.
  Credit if the wrong-day/window or the UTC-vs-NY day mismatch is identified.
- P5 CSV written to the worker pod's /tmp; a separate CronJob pod cannot read
  it (and /tmp is lost on restart).
- P6 Redis/Redlock is unnecessary for a single-replica worker / does not record
  completion; Postgres or CronJob concurrencyPolicy suffices.
- P7 Amount unit risk: sending integer cents to a Ledgerly endpoint that takes
  major units (100x error), or the unverified "bulk accepts cents" claim.
  Credit as a FINDING only if presented as a defect or must-fix risk; record
  "gap-only" if it appears only as an open question / evidence gap.

Decoy: keeping `console.log` JSON logging is fine; flagging it as a defect is
INVALID.

Bonus valid items (count, do not score as key): float `amount * 100` in JS;
v1/v2 id parity for dedupe; pg returns bigint as string; Express 4 async errors
crash the process; stranded `sending`/`failed` rows; CSV contract; table
rewrite lock; 10k bulk cap vs 9k peak; CronJob timeZone; missing SIGTERM
handling; readiness probe.

Also count INVALID findings (wrong or manufactured).
