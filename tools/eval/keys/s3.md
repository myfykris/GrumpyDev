# Answer key: S3 (subtle traps: scale-out plan)

Ten planted defects. Credit an item only if the review identifies the specific
mechanism (not just a vague "check X"). Partial credit (0.5) when it names the
right area and a related but incomplete or partly wrong mechanism.

- K1 PgBouncer transaction pooling breaks session-level advisory locks: the
  lock is held by a PgBouncer server connection, not the worker, so leader
  identity is meaningless (lock can be "re-acquired" on the same backend by
  another worker -> two leaders, or survives the leader's death -> no
  failover). Credit if it says session advisory locks / leader election do not
  work through transaction pooling.
- K2 Non-leaders' blocked `pg_advisory_lock` calls hold a pool client /
  PgBouncer server connection indefinitely (connection starvation), and the
  promise never settles.
- K3 `CREATE INDEX CONCURRENTLY` cannot run inside a transaction block; the
  migration Job wraps each file in a transaction, so migration 002 fails.
- K4 Adding the foreign key validates every existing row while holding a lock
  that blocks writes on invoices; should use NOT VALID then VALIDATE
  CONSTRAINT. (Also acceptable: noting the lock/scan cost of the FK add.)
- K5 Nothing inserts new customers going forward: after the FK exists, every
  webhook for a customer not already in `customers` fails the FK and the
  invoice is lost/crashes the handler.
- K6 Liveness probe depends on the database (SELECT 1) with failureThreshold 1:
  a DB or PgBouncer blip restarts every server pod at once (cascading outage);
  liveness should not check dependencies (use readiness instead).
- K7 Shutdown: no readiness probe / preStop delay, so endpoint removal races
  SIGTERM and new requests hit a closing server during rollouts; and/or
  `server.close` waits on keep-alive connections from the ingress until the
  grace period kills the pod. Credit either mechanism.
- K8 Rate limiter keyed by req.ip behind NGINX ingress without
  `trust proxy`: every request appears to come from the ingress, so all callers
  share one bucket (any caller can exhaust Partner's quota / Partner gets
  429s); and/or per-replica in-memory counters. Credit the shared-bucket /
  wrong-client-IP mechanism; per-replica-only is 0.5.
- K9 Lock queue: the "instant" ADD COLUMN needs an ACCESS EXCLUSIVE lock, waits
  behind the report's 5-minute REPEATABLE READ transaction, and every insert
  and claim queues behind it -> webhook outage; needs lock_timeout or timing
  outside the report window.
- K10 Batch 500 with a 1 s tick under setInterval: ticks overlap (a tick of 500
  sequential requests takes far longer than 1 s) -> unbounded concurrent
  requests to Ledgerly and DB; Ledgerly rate limits unknown.

Decoys (do NOT credit as defects; count as INVALID if called a defect):
- SKIP LOCKED with 3 worker replicas is correct.
- PgBouncer transaction pooling by itself is fine for this app's plain
  queries; the defect is only its interaction with session features (K1/K2).

Also count other findings: VALID (correct, specific, beyond the key) vs
INVALID (wrong or manufactured).
