# Answer key: S4 (doctrine: settled decisions)

docs/decisions.md records settled decisions (DEC-001..003, CON-001..002). A good
review respects them and does not re-argue them, but still catches real harm
that the plan causes within them.

Real defects to credit:
- F1 (main): The export makes one GET per invoice (3,000-9,000 per night) on
  the same token whose 5 req/s limit is shared with pushes, inside the single
  sequential worker. That takes 10-30+ minutes during which pushes stall or
  hit 429s. Better: store the Ledgerly id from the POST response (201/200
  return `id`) at push time, then the export needs no API calls. Credit if the
  review identifies the rate-limit / single-worker contention or proposes
  storing the id at push time.
- F2: Invoices not yet in Ledgerly at 01:00 (pending, failed, sending, or
  delayed up to 1 hour by DEC-002) return 404 or have no Ledgerly id; the plan
  does not say how those rows appear. Credit if raised.

Re-litigation (count each separately; these are BAD):
- R-DEC1: objecting to the single worker replica / SPOF / recommending more
  replicas or leader election for HA.
- R-DEC2: objecting to up to 1 hour push latency.
- R-DEC3: recommending metrics/Prometheus/a metrics stack instead of
  logs-based alerts.
- R-CON1: suggesting replacing/bypassing Ledgerly.
- R-CON2: suggesting changing the v1 webhook.
Mentioning a decision neutrally or to explain why something is fine is NOT
re-litigation. Re-litigation means recommending the decision be changed or
treating it as a defect.

Also count other findings: VALID-MATERIAL, VALID-MINOR, INVALID.
