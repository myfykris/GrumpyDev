# Answer key: S5 (diff review: implementation of docs/plans/reliable-pushes.md)

The uncommitted diff implements the reliable-pushes plan with eight planted
defects. Credit an item only if the review identifies the specific defect.

- B1 Reclaim condition is inverted: `claimed_at > now() - interval '15 minutes'`
  reclaims rows claimed in the last 15 minutes (in flight) and never reclaims
  stale ones. Should be `<`.
- B2 Backoff unit bug: `backoffMs` returns milliseconds but is passed to
  `make_interval(secs => $2)`, so delays are 1000x too long (up to 1000 hours).
- B3 409 is always `failed`: `duplicate_external_id` must be `sent` per the plan
  and docs/ledgerly-api.md; as written those rows retry until `dead` and page
  on-call for invoices already in Ledgerly. (Credit also if it says 409 codes
  are not distinguished.)
- B4 Missing `await` on the `UPDATE ... status = 'failed'` query: a rejected
  promise is unhandled (Node 22 exits the process), and/or ordering races with
  the next claim.
- B5 SIGTERM handler calls `process.exit(0)` immediately: no graceful finish of
  the in-flight request, contradicting the plan's shutdown design.
- B6 Tests miss what the plan promised: no 409 case (which would have caught
  B3), no integration test, no kill test, no reclaim test.
- B7 Migration uses `DEFAULT clock_timestamp()` (volatile) for
  next_attempt_at: forces a full table rewrite of ~600k rows under ACCESS
  EXCLUSIVE (lock_timeout does not bound the rewrite), and contradicts the
  plan (no default / NULL). Credit also if it flags the default as deviating
  from the plan with a concrete consequence.
- B8 deploy/worker.yaml is not changed to `Recreate` as the plan requires, so
  old and new workers overlap during the rollout (old worker's rows have
  claimed_at NULL and are reclaimed immediately -> concurrent sends).

Decoys (not defects): full-jitter via Math.random; ORDER BY id; 20 s timeouts.

Also count other findings: VALID-MATERIAL, VALID-MINOR, INVALID.
